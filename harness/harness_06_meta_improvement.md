# 개선(메타) 계층 (Layer 3 — 하네스 자체를 진화시키기)

> 지금 만든 5+1개 문서(00~05)는 "현재 시점의 최선"일 뿐, 정답이 아닙니다.
> 실제로 써보면 안 쓰이는 필드, 빠진 필드가 드러납니다. 이 계층은

## 3. 실패 패턴 라이브러리

> 개별 실수가 아니라 "반복되는" 실수만 여기에 등록합니다.
> 새 프로젝트 시작 시 이 목록을 먼저 훑고, 해당하는 것은 TRD/작업지시서 체크리스트에
> 선제적으로 반영합니다.

| 패턴 | 설명 | 재발 방지책 |
|---|---|---|
| 스펙-실제 불일치 | 문서화된 스펙(레거시 코드 분석, 요구사항 문서 등)과 실제 구현 대상이 다름 | 에이전트에게 "원본을 직접 재검증"을 원칙으로 강제 (execution_infra §4 에스컬레이션 프로토콜 연동) |
| 암묵적 완료 가정 | "이건 이미 다른 데서 구현됐을 것"이라고 가정하고 넘어갔다가 실제로 없었음 | 작업지시서 §0 전제조건에서, 의존하는 선행 기능의 실제 코드 위치를 명시하고 확인하게 함 |
| 문서 유형 혼동 | TRD를 복사해서 작업지시서인 척 제출 | 00_overview의 파일명 규칙 + 템플릿 헤더로 구분 강제 |
| 파일명 인코딩 문제 | 한글/공백 섞인 파일명이 특정 환경에서 안 열림 | 파일명 규칙(영문/숫자)을 00_overview에 고정 |
| ADR 대상 결정이 기록 없이 그냥 진행됨 | 삭제정책/동시성처리/인증방식 등 `harness_08` 체크리스트에 명백히 해당하는 결정이 요구사항서·TRD 안에는 있지만 ADR로는 하나도 안 남아 있었음(attend 프로젝트 A0~A1에서 발견, 2026-09-04) | 단위 TRD 확정 직후 "이 중 ADR 체크리스트에 해당하는 게 있는가"를 작업지시서 §0에서 한 번 더 확인하는 절차 추가 검토. 발견 즉시 소급 작성(`docs/{project}_adr.md`)으로 만회 가능 |
| 문서 간 상호참조 깨짐 | 마스터TRD/작업지시서가 아직 존재하지 않는 문서(`attend_env_setup.md`)를 참조 — 파일을 만들기로 "말"만 하고 실제로 안 만듦 | 문서에 다른 파일 경로를 적을 때, 그 자리에서 파일이 실제로 존재하는지 확인하는 습관화. `harness_19` 템플릿 검증 스크립트가 생기면 깨진 링크 검사도 포함 |
| 보안 정책이 기술스택 결정보다 늦게 채워짐 | Phase A 순서(기술컨벤션 먼저 확정 → 단위 TRD)를 실제로는 안 지키고, 단위 TRD(A1)에서 인증방식(세션쿠키)까지 먼저 확정된 뒤에야 `harness_13`이 비어있다는 게 드러남. 그 결과 CSRF/쿠키보안속성 같은 정책이 구현 직전까지 빠진 채로 방치될 뻔함 | 단위 TRD에서 인증/세션 관련 결정이 나오면, 그 자리에서 즉시 전역 기술컨벤션 문서에 소급 반영하고 관련 보안 속성(CSRF, 쿠키 플래그 등)을 짝지어 검토하는 것을 습관화 |
| PR 부분 병합 | "구현 완료" PR이 실제로는 TRD/작업지시서 문서만 병합되고 소스코드 커밋은 같은 브랜치에 계속 쌓이기만 한 채 base로 병합되지 않음 (2026-09-05, attendance-app A1에서 발견 — `feature/a1-login`이 4커밋 앞선 채 미병합) | 병합 전 `git merge-base --is-ancestor <base> <feature-branch>` 역방향 확인을 머지 체크리스트에 추가; GitHub 브랜치 보호 규칙(리뷰 필수 + 상태 체크)으로 "일부만 병합된 PR"을 구조적으로 차단 |
| .gitignore 부재로 인한 오염 | 브랜치를 로컬에서 오가며 생긴 `__pycache__` 등 빌드 산출물이 `.gitignore` 부재로 base 브랜치에 그대로 커밋됨 (2026-09-05 발견 — base엔 `.pyc`만 있고 원본 `.py`는 없어 "코드 실종"처럼 보임) | 프로젝트 착수 즉시(harness_05 실행 전) 스택에 맞는 `.gitignore`부터 커밋; 커밋 전 `git status`로 스테이징 내용 diff 확인을 습관화 |
| 정책 확정 순서 역전 | 데이터모델(컬럼)은 이미 "확정"됐는데 그 컬럼이 다루는 민감정보의 생애주기/마스킹 정책은 여전히 "미결"로 남아, 되돌리기 어려운 결정(CLAUDE.md 원칙 8)이 사실상 먼저 굳어짐 (2026-09-05, attendance-app `students.contact`/`guardian_contact`) | A0 데이터모델 TRD에 PII 성격 컬럼이 포함되면, `harness_10_data_lifecycle.md` 정책 확정을 데이터모델 "확정" 전 선행 조건으로 강제 |
| 미병합 브랜치 임의 삭제로 dangling commit 소실 위험 | 1차 점검(위 "PR 부분 병합")에서 미병합 상태로 확인됐던 `feature/a1-login`이, 5시간 뒤 재점검 시점엔 원격에서 아예 삭제되어 있었음. `git fsck`로 dangling commit(코드리뷰 반영까지 끝난 최종본)을 겨우 발견해 `recovered/a1-login`으로 복구 — `git gc` 타이밍에 따라 영구 소실될 수도 있었음 (2026-09-05, attendance-app) | "병합 확인 전 브랜치 삭제 금지"를 머지 체크리스트에 명시; GitHub 저장소에서 "Automatically delete head branches"를 끄거나, 최소한 병합 확인(§ 위 규칙) 없이 삭제하지 않는 것을 절차로 강제 |
| 기준 브랜치 선언과 실제 운영 불일치 | CLAUDE.md는 `PROD_SCH`를 기준 브랜치로 선언했지만, 실제로는 `PROD`에서 작업해 `PROD_SCH`는 `PROD`를 머지만 받는 하위 브랜치로 쓰임 — 그 결과 선언상의 기준 브랜치엔 실제 산출물이 하나도 없음 (2026-09-05, attendance-app) | 프로젝트 착수 시 기준 브랜치를 딱 하나만 선언하고, 실제 `git push`/PR 대상이 그 선언과 일치하는지 매 PR마다 확인 (자동화하려면 CI에서 PR 대상 브랜치가 문서상 기준 브랜치와 동일한지 체크) |

(프로젝트를 진행하면서 이 표는 계속 늘어납니다. 이게 이 계층의 존재 이유입니다.)
