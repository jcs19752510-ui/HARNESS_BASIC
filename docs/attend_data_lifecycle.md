## §1. 적용 법령/근거 [사람 작성 — 법무 검토 권장]
- 대상: 미성년 학생 본인 연락처(`contact`) + 법정대리인(보호자) 연락처(`guardian_contact`)
- 관련 법령 후보: 개인정보보호법(대한민국) — 미성년자 개인정보는 통상 법정대리인 동의 요건이
  더 엄격하게 적용됨. **AI는 이를 법률 자문으로 단정하지 않으며, 실제 적용 여부는 사람의
  법무 검토가 필요합니다.**
- 이 조직이 개인정보보호법상 어떤 처리자 유형(소규모 조직 특례 대상 여부 등)에 해당하는지도
  사람이 확인해야 확정 가능한 항목입니다.

## §2. 데이터 항목별 보존기간 — 후보안 3개 [사람 선택 필요]

| 데이터 항목 | 민감도 | 현재 스키마 상태 |
|---|---|---|
| `students.contact` (학생 연락처) | 높음 | 평문 컬럼, 마스킹/암호화 없음 |
| `students.guardian_contact` (보호자 연락처) | 높음 | 평문 컬럼, 마스킹/암호화 없음 |
| `students.*` 기타(이름/학년/사진 등) | 중간 | `use_yn` 소프트삭제만 적용 |

### 후보 A — "최소 변경" (당장 코드 변경 없음, 정책만 문서화)
- 보존기간: `use_yn='N'`(전학/졸업 등 비활성화) 후 **1년**간 조회 가능 상태 유지 → 이후
  익명화(연락처를 `****`로 치환, 이름은 유지) 배치 작업 실행
- 화면 노출: 마스킹 없음 — 담임교사 이상 역할은 전체 번호 그대로 조회 (현재 A1의 4개 역할
  전부가 이미 "전체 개방" 권한 정책이므로 이 컬럼만 예외를 둘지가 쟁점)
- 장점: 구현 비용 최소. 단점: 활성 학생 데이터는 평문 그대로 오래 남을 수 있음

### 후보 B — "화면 마스킹 + 장기 보존"
- 보존기간: `use_yn='N'` 후 **졸업/전학 학년도 종료 기준 3년**까지 보관 (교육기관 관례상
  민원/문의 대응 목적 — 실제 요구되는 기간은 법무 확인 필요) 후 물리적 익명화
- 화면 노출: 목록 화면에서는 `010-****-1234`처럼 뒷자리만 마스킹, 상세 화면에서만 전체 번호
  노출(클릭 시 로그 기록) — `attendance_history`처럼 "누가 열람했는지" 별도 감사 테이블 필요
- 장점: 화면 유출 위험 감소, 열람 감사 가능. 단점: 상세화면 열람 로그용 신규 테이블 필요 →
  A0 데이터모델에 소급 추가 필요(데이터모델 변경이므로 이것도 사람 승인 대상)

### 후보 C — "역할별 차등 접근"
- 보존기간: 후보 B와 동일
- 화면 노출: `users.role`별로 연락처 열람 권한 자체를 분리 — 예: 담임교사만 전체 열람,
  임원교사/교역자는 마스킹된 값만 (현재 요구사항 정의서 §3에 "역할별 접근 가능 범위는 전체
  개방, 화면 단위 권한만 구분"이 이미 ✅확정으로 돼 있어 **이 후보를 택하면 그 기존 확정
  사항과 충돌** — 두 결정 중 하나를 재검토해야 함)
- 장점: 최소 권한 원칙에 가장 부합. 단점: 이미 "확정"된 권한 정책과 충돌하므로 변경관리
  절차(`harness_12`) 밟아야 함

## §3. 파기 절차 (선택된 후보안에 맞춰 구체화 예정)
`harness_10` §3의 표준 흐름(트리거→대상목록→승인→파기→로그) 그대로 적용 가능. 트리거는
"졸업/전학으로 `use_yn='N'` 처리"가 될 것으로 보이나, 실제 파기 배치 작업/승인자 지정은
후보안 확정 후 별도 작업지시서로 구체화.

## §4. 열람/정정 요청 처리 절차
현재 A1~A6 TRD 어디에도 "보호자가 직접 열람/정정을 요청하는 화면"은 범위에 없음 (교사가
대신 입력/수정하는 구조). 보호자 셀프서비스 화면이 없다면 이 절차는 "보호자가 담임교사에게
요청 → 교사가 학생정보 화면에서 수정"하는 수동 절차로 대체 가능 — **이것도 범위 확인이 필요한
사람 결정 사항**(요구사항 정의서에 명시적으로 없던 내용이라 임의로 화면을 추가하지 않음).
