> 이 문서는 harness_01_trd_template.md의 §0-1(비기능 요구사항)과
> §3(워크플로우)를 채우기 위한 상위 결정 사항입니다.
> 마스터 TRD 작성 시 이 문서를 기준으로 반영합니다.

## 1. 기능 요구사항 (핵심 정책)

| 항목 | 결정 |
|---|---|
| 등록 주체 | 교사가 반별로 일괄 등록 (학생 개별 체크인 없음) |
| 출결 상태 종류 | 출석 / 결석 / 지각 (3종) |
| 수정/취소 권한 | 교사/관리자는 기간 제한 없이 언제든 가능 |
| 반(클래스) 구조 | 학생 1명 = 반 1개에만 소속 (다중 소속 없음) |
| 등록 주기 | 특정 요일만 (예: 주일학교 — 매일 아님) |

## 2. 비기능 요구사항 (반드시 TRD §0-1에 반영)

### 동시성
- **정책:** 같은 반에 담임교사+보조교사 등 **여러 명이 동시에 등록 가능**
- **충돌 처리 방식(확정):** 마지막 저장자 우선(단순 덮어쓰기). 실시간 잠금/알림 없음.
  단, 감사 추적(아래)에서 모든 저장 이벤트(이전 값 포함)를 기록하므로 데이터 유실은 아니며,
  사후에 "누가 언제 어떤 값으로 덮어썼는지" 확인 가능
- **설계 함의:** 별도 낙관적 잠금/실시간 알림 인프라 불필요. 저장 API는 단순 UPSERT로 구현하되,
  UPSERT 직전 값을 반드시 감사 로그에 남기는 순서로 구현

### 권한 (4단계)
- 관리자 / 담임교사 / 임원교사 / 교역자
- **접근 범위:** 4개 역할 모두 전체 반에 대해 등록/수정/조회 가능 (반별 접근 제한 없음)
- **설계 함의:** 역할 구분은 "어떤 화면/기능에 접근 가능한가"(예: 관리자 전용 설정 화면)를
  가르는 용도이지, "어떤 반 데이터를 볼 수 있는가"를 가르는 용도가 아님.
  TRD §1(데이터구조)의 권한 체크는 반(class) 단위 필터링 없이 역할(role) 단위로만 구현

### 감사 추적 (Audit Trail)
- **정책:** 필요 — 출결 기록의 모든 변경에 대해 **누가/언제/무엇을 바꿨는지** 기록
- **설계 함의:** 출결 테이블과 별도로 변경이력 테이블(또는 변경 로그) 설계 필요.
  단순 UPDATE로 값만 덮어쓰면 안 되고, 이전 값·이후 값·변경자·변경시각을 남기는 구조 필요

### 삭제 정책
- **정책:** 물리 삭제(DELETE) 허용 안 함 — `use_yn` 소프트 삭제만 사용
- **설계 함의:** 모든 삭제성 작업은 `use_yn = 'N'` 처리로 구현. 관리자 포함 예외 없음

### 개인정보
- 학생 개인정보(연락처 등) 취급 정책은 데이터모델 설계 단계에서 별도 확정 필요 (미결)

## 3. 다음 단계로 넘어가기 전 남은 미결 항목

| 항목 | 상태 |
|---|---|
| 역할별(4단계) 접근 가능 범위 매트릭스 | ✅ 확정 (전체 개방, 화면 단위 권한만 구분) |
| 동시 등록 충돌 처리 방식 | ✅ 확정 (마지막 저장자 우선 + 감사 로그) |
| 개인정보(학부모 연락처 등) 보유 여부 및 마스킹 정책 | 미결 |
| 통계/현황 화면 필요 여부 | 아직 논의 안 함 |
