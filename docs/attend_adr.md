### ADR-001: 삭제 정책 — 소프트 삭제 전용
- 날짜: 2026-09-02
- 상태: 승인됨(소급기록)
- 결정권자: 프로젝트 담당자(요구사항 정의서 확정 시점)

**배경 (Context)**
출결/학생/반 데이터는 실수로 지워지면 복구가 어렵고, 감사 추적(누가 언제 무엇을
바꿨는지)이 프로젝트 필수 요건이다. 물리 삭제를 허용하면 이력 자체가 사라진다.

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| 물리 삭제(DELETE) 허용 | 구현 단순, 저장공간 절약 | 실수 삭제 복구 불가, 감사 이력 단절 |
| 소프트 삭제(`use_yn`)만 허용 | 실수 복구 가능, 이력 보존 | 조회 시 `use_yn='Y'` 필터를 모든 쿼리에 강제해야 함(누락 리스크) |

**결정 (Decision)**
모든 테이블에서 물리 삭제를 금지하고 `use_yn` 컬럼으로만 소프트 삭제한다.
관리자 권한이라도 예외를 두지 않는다 (`docs/attend_requirements_summary.md` §2 삭제 정책).

**결과/트레이드오프 (Consequences)**
- 모든 SELECT 쿼리/ORM 쿼리에서 `use_yn='Y'` 필터 누락 시 삭제된 데이터가 노출되는
  버그 클래스가 생긴다 → `docs/attend_tech_conventions.md`의 ORM 공통 스코프(soft-delete
  filter) 규칙으로 보완 필요(A2 구현 시 확정).
- 실제 개인정보 파기(법적 요청)는 소프트 삭제로 대체되지 않는다 — `harness_10`
  개인정보 생애주기 정책이 별도로 필요(이번 스코프 아님, 사람 결정 대기).

**관련 문서**
관련 TRD: `docs/trd/attend_a0_datamodel_trd.md`

### ADR-002: 동시성 처리 — UPSERT + 마지막 저장자 우선 + 변경이력 감사
- 날짜: 2026-09-02
- 상태: 승인됨(소급기록)
- 결정권자: 프로젝트 담당자(요구사항 정의서 확정 시점)

**배경 (Context)**
같은 반에 담임+보조교사 등 여러 명이 동시에 출결을 등록할 수 있다. 실시간
잠금/알림 인프라 없이도 데이터 유실 없이 처리해야 한다.

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| 낙관적 잠금(버전 컬럼 + 충돌 시 거부) | 유실 방지, 충돌 명시적 처리 | 구현 복잡, 충돌 시 UX 설계 필요(누구 것을 살릴지 사용자가 판단) |
| 마지막 저장자 우선(단순 덮어쓰기) + 이전 값 이력 기록 | 구현 단순, 등록 흐름이 끊기지 않음 | 두 교사가 동시에 다르게 입력하면 하나는 조용히 사라짐(단, 이력에는 남음) |

**결정 (Decision)**
저장 API는 단순 UPSERT로 구현하고, UPSERT 직전 값을 반드시 `attendance_history`에
먼저 기록한다. 최종값은 마지막 저장자 것으로 남되, 모든 시도가 이력에 보존되어
사후 확인이 가능하다.

**결과/트레이드오프 (Consequences)**
- 동시 저장 시 사용자에게 "누군가 방금 바꿨다"는 실시간 경고는 없다 — 필요해지면
  추후 별도 단위(알림/폴링)로 재검토.
- 이력 테이블(`attendance_history`)에 기록을 남기는 순서가 저장 로직의 핵심
  불변조건이 된다 — A5(출결 등록) 구현 시 트랜잭션 순서(이력 기록 → UPSERT, 또는
  같은 트랜잭션 내 원자적 처리) 확정 필요.

**관련 문서**
관련 TRD: `docs/trd/attend_a0_datamodel_trd.md`, `docs/attend_requirements_summary.md`

### ADR-003: 인증 방식 — 서명 쿠키 기반 세션 (JWT 미사용)
- 날짜: 2026-09-03
- 상태: 승인됨(소급기록)
- 결정권자: 프로젝트 담당자(A1 TRD 확정 시점)

**배경 (Context)**
서버사이드 렌더링(Jinja2) 기반 웹앱이고 별도 모바일/외부 API 클라이언트가 없다.
로그인 인증 상태를 서버가 관리할 방식을 정해야 한다.

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| JWT(토큰을 클라이언트가 보관) | 서버 상태 불필요, API 클라이언트 확장 용이 | 폼 기반 앱에서 저장 위치(localStorage 등)가 XSS에 취약, 즉시 무효화(로그아웃) 구현이 번거로움 |
| 서명된 쿠키 세션(itsdangerous + FastAPI SessionMiddleware) | 브라우저가 자동 전송, 즉시 무효화 쉬움, 폼 기반 앱과 궁합이 좋음 | 별도 API 클라이언트가 생기면 재검토 필요, CSRF 방어가 별도로 필요(→ ADR-006) |

**결정 (Decision)**
서명된 쿠키 기반 세션을 사용한다. 별도 세션 테이블 없이 서버가 서명 검증만
수행한다(`docs/trd/attend_a1_trd.md` §1).

**결과/트레이드오프 (Consequences)**
- 세션 쿠키 특성상 CSRF 공격에 노출된다 — 별도 방어 정책이 반드시 필요
  (→ ADR-006, `docs/attend_tech_conventions.md` §3).
- 추후 외부 API(모바일 앱 등)가 필요해지면 이 결정을 재검토해야 한다 — 그때는
  본 ADR을 "대체됨(ADR-xx로)"으로 상태 변경.

**관련 문서**
관련 TRD: `docs/trd/attend_a1_trd.md`

### ADR-004: 비밀번호 저장 — bcrypt 해시
- 날짜: 2026-09-03
- 상태: 승인됨(소급기록)
- 결정권자: 프로젝트 담당자(A1 TRD 확정 시점)

**배경 (Context)**
로그인 비밀번호를 저장해야 하는데, 평문 저장은 CLAUDE.md/하네스 원칙상 명백히
금지된다(개인정보 보호 원칙).

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| bcrypt | 널리 검증된 적응형 해시, 라이브러리 성숙 | 매우 긴 입력(72바이트 초과)은 잘림 — 실무상 문제 거의 없음 |
| argon2 | 최신 권장 알고리즘, GPU 공격에 더 강함 | 생태계/러닝커브가 상대적으로 더 필요 |

**결정 (Decision)**
bcrypt를 사용한다(`docs/trd/attend_a1_trd.md` §1). 비밀번호 원문은 어떤 로그/DB에도
남기지 않는다.

**결과/트레이드오프 (Consequences)**
- 알고리즘 자체는 충분히 안전하나, 최소 복잡도 규칙이 "8자 이상"으로만 확정되어
  있어(A1 TRD §7) 약한 비밀번호 자체는 막지 못한다 — A2(계정 생성)에서 재검토 여지로
  이미 명시됨.

**관련 문서**
관련 TRD: `docs/trd/attend_a1_trd.md`, `docs/trd/attend_a0_datamodel_trd.md`

### ADR-005: 학생 식별자 — 시스템 PK + 별도 자동생성 student_no
- 날짜: 2026-09-02
- 상태: 승인됨(소급기록)
- 결정권자: 프로젝트 담당자(A0 데이터모델 확정 시점)

**배경 (Context)**
동명이의 학생을 구분하고, 화면에 노출할 안정적인 학번 표기가 필요하다.

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| 이름만으로 구분 | 별도 컬럼 불필요 | 동명이의 구분 불가 |
| PK만 노출 | 구현 단순 | 내부 일련번호를 화면에 그대로 노출하는 것은 사용자 경험상 부적절 |
| PK(내부용) + `student_no`(순번 자동생성, 화면 노출용) 이원화 | 동명이의은 PK로 항상 구분, 화면은 사람이 읽기 쉬운 번호 사용 | 컬럼 하나 추가, 채번 로직 필요 |

**결정 (Decision)**
`students.id`(PK)로 시스템 내부 구분을 항상 보장하고, `student_no`(자동 순번)를
화면 노출용으로 별도 채번한다. 화면 표시는 `student_no` + 이름 병기를 권장한다
(`docs/trd/attend_a0_datamodel_trd.md` §5).

**결과/트레이드오프 (Consequences)**
- 채번 규칙(연도별 리셋 여부, 자릿수 등) 세부사항은 A4(학생 관리) TRD 작성 시점에
  확정 필요 — 아직 미결.

**관련 문서**
관련 TRD: `docs/trd/attend_a0_datamodel_trd.md`

### ADR-006: CSRF 방어 방식 — 세션 바인딩 토큰 (Synchronizer Token)
- 날짜: 2026-09-04
- 상태: 제안됨(기본값 채택 — A1 구현 착수 전 재확인 권장)
- 결정권자: (하네스 리뷰에서 기본값 제안 — 최종 확정은 A1 구현 착수 전 사람 확인 필요)

**배경 (Context)**
ADR-003에서 서명 쿠키 기반 세션 인증을 채택했다. 세션 쿠키 인증 + 서버사이드
폼 제출 조합은 CSRF(Cross-Site Request Forgery)에 가장 취약한 구조인데, A1 TRD와
`harness_13` 어디에도 CSRF 방어 정책이 없었다(하네스 리뷰에서 발견).

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| 방어 없음(현행) | 구현 비용 0 | 로그인된 교사 브라우저를 이용해 공격자가 출결 데이터를 임의로 조작하는 요청을 강제할 수 있음 — 감사 이력엔 "정상 교사"가 한 것으로 남아 원인 추적도 어려워짐 |
| Synchronizer Token(서버가 세션에 토큰 저장, 폼 hidden field로 발급 → 제출 시 대조) | FastAPI/Jinja2 서버사이드 렌더링 구조와 자연스럽게 맞음, 구현이 비교적 단순 | 모든 상태변경 폼에 토큰 삽입을 빠짐없이 적용해야 함(누락 리스크는 코드리뷰/린트로 보완) |
| Double Submit Cookie | 서버 세션 저장 불필요 | 쿠키 값을 JS로 읽어 헤더에 실어야 해서 서버사이드 폼 위주 구조엔 배선이 더 필요 |

**결정 (Decision)**
Synchronizer Token 방식을 기본값으로 채택한다. 모든 상태변경 요청(POST/향후
PUT/DELETE 대응 액션 경로)에 세션 바인딩 CSRF 토큰을 hidden field로 요구한다.
GET 요청에는 적용하지 않는다.

**결과/트레이드오프 (Consequences)**
- A1(로그인) 구현 시 로그인 폼 자체에도 적용해야 하는지, 로그인 이전(미인증)
  상태의 CSRF는 범위에서 제외할지 결정 필요 — 통상 로그인 폼은 세션이 없으므로
  제외하고 로그인 "이후" 상태변경 요청부터 적용하는 것을 권장.
- 이 결정은 아직 코드로 구현되지 않았다(A1 코드 미착수) — 실제 구현 시작 전에
  담당자가 최종 확인 후 상태를 "승인됨"으로 바꿀 것.

**관련 문서**
관련 TRD: `docs/trd/attend_a1_trd.md` (구현 시 §2/§4/§5 AC에 반영 필요)
관련 컨벤션: `docs/attend_tech_conventions.md` §3

### ADR-007: 세션 쿠키 보안 속성 — HttpOnly/Secure/SameSite=Lax
- 날짜: 2026-09-04
- 상태: 제안됨(기본값 채택 — A1 구현 착수 전 재확인 권장)
- 결정권자: (하네스 리뷰에서 기본값 제안 — 최종 확정은 A1 구현 착수 전 사람 확인 필요)

**배경 (Context)**
A1 TRD §5(AC)는 "세션 쿠키가 발급된다"까지만 검증하고, 쿠키의 보안 속성
(스크립트 접근 차단, HTTPS 전용 전송, 크로스사이트 전송 제한)은 AC에 없었다.

**검토한 대안 (Options)**
| 대안 | 장점 | 단점 |
|---|---|---|
| 속성 미지정(브라우저 기본값) | 구현 신경쓸 것 없음 | XSS로 쿠키 탈취 가능(HttpOnly 없으면), 평문 HTTP로도 전송 가능(Secure 없으면) |
| HttpOnly + Secure + SameSite=Lax | JS로 쿠키 접근 불가, HTTPS 전용, 일반적인 크로스사이트 요청에서 쿠키 미전송(로그인 링크 등 최상위 이동은 허용) | 로컬 개발(HTTP)에서는 Secure 속성 때문에 환경별 분기 필요 |

**결정 (Decision)**
운영 환경에서는 `HttpOnly=true`, `Secure=true`, `SameSite=Lax`를 모두 적용한다.
로컬 개발(HTTP) 환경에서는 `Secure` 속성만 환경변수로 끌 수 있게 하되, 기본값은
켜진 상태로 한다.

**결과/트레이드오프 (Consequences)**
- 로컬 개발 시 `Secure=true`인 채로 HTTP로 접속하면 쿠키가 저장되지 않아 로그인이
  안 되는 것처럼 보일 수 있다 — `docs/attend_env_setup.md`에 로컬 환경변수 안내 필요.
- 이 결정도 아직 코드로 구현되지 않았다 — A1 구현 착수 전 최종 확인 필요.
